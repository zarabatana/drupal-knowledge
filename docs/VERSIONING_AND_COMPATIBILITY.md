# Versioning and Compatibility

What `1.1.3` means, contract by contract. Drupal Knowledge is not one
version number: it is one product release number and a family of contract
versions that deliberately move on their own schedules. This document
enumerates every one of them, states the compatibility promise each carries
through the 1.x series, and tells a consumer exactly what to pin — and what
never to pin.

One honesty note before any promise: a version number is a statement about
*shape stability*, never about analysis truth. Nothing in this document
claims the product guarantees security, ensures compliance, finds every
vulnerability or proves an upgrade safe. A `1.0` contract can carry an
`unknown`, and it will keep carrying it.

## The version taxonomy

**The product release version** is the file `VERSION` at the repository
root — `1.1.3` for this release. It names a released tree: the knowledge
records, the engines, the schemas and the code that shipped together and
were validated together. It follows a semantic discipline (major.minor.patch)
over the release as a whole.

**Contract versions** name the shape of one specific interface or stored
record. They are declared as constants in code, embedded in the records and
responses they govern, advertised by `dk version --json`, and validated by
`python3 scripts/dk.py validate`. They version independently of the release
on purpose: a new engine contract must not force every consumer to change,
and pinning them all to the release number would force a major version every
time a security advisory arrives.

The real contracts and their values at `1.1.3` (unchanged since `1.0.0`):

### Public surfaces

| Contract | Value | Where declared |
|---|---|---|
| Public API version (route family `/api/v1`) | `API_VERSION = "1"` | `scripts/dk_api.py` |
| Public API contract | `API_CONTRACT_VERSION = "1.0"` | `scripts/dk_api.py` |
| Public dataset schema | `PUBLIC_DATASET_SCHEMA_VERSION = "0.1"` | `scripts/dk_public.py` |
| Query interface | `QUERY_INTERFACE_VERSION = "0.1"` | `scripts/dk_query.py` |
| Query result contract | `RESULT_CONTRACT_VERSION = "0.1"` | `scripts/dk_query.py` |

The public API is `1.0` because its envelope is a promise to strangers. The
dataset schema and query interface behind it stay `0.1`: they are build
inputs the API and website consume, not contracts offered to third parties,
and the dataset manifest says so in its own `api_status` field.

`0.x` means exactly what it says: these shapes may still change within the

announced in the changelog, and never by rewriting a stored record. A
record keeps the version it was written under.

### Release metadata

`release/sbom.json` and `release/checksums.json` carry their own
`sbom_contract_version` and `checksums_contract_version` (`1.0`). They are
regenerated by `dk release-meta` and byte-compared by `dk validate`.

## Compatibility promises for 1.x

### Public API (`/api/v1`, contract `1.0`)

- **Additive only.** New fields, new optional query parameters and new
  routes may appear within 1.x. Existing fields are never removed and never
  repurposed: a field that meant one thing in `1.0` means that thing for as
  long as it exists. A consumer must tolerate fields it does not recognize.
- **`unknowns` is always present** in the envelope and is never emptied to
  look tidy. It never becomes a pass.
- **`dataset_id` changes with content and with release, by design.** It is
  derived from the dataset's own canonical bytes, and those bytes include
  the DK release version. It is a content identity, not an API version — a
  new advisory or a new release produces a new `dataset_id` while the
  `api_contract_version` stays `1.0`. Never treat `dataset_id` stability
  as an API compatibility signal.
- **Every response carries `api_contract_version`, `dk_version` and
  `dataset_id`; every result carries `trust_class` and `trusted_knowledge`.**
  These fields exist in `1.0` and will exist in every 1.x response.
- The API remains read-only: no verb but GET, HEAD and OPTIONS is routable.

### CLI (`dk`)

- Community commands (`status`, `project`, `search`, `explain`,
  `provenance` and the rest of `dk --help`) keep their names and their
  `--json` output shapes additive through 1.x.
- Human-readable output is not contract surface and may be reworded in any
  release. Script against `--json`.
- No 1.x release adds a flag that promotes a source snapshot, a discovery
  signal or a project observation into trusted knowledge. That is a boundary,
  not a feature gap.

### Stored records

- Canonical records under `knowledge/`, `security/`, `api/`, `rules/`,
  `cases/`, `discovery/` and `sources/` keep the contract version they were
  written under. A contract increment never rewrites existing records.
- Source snapshots are immutable and content-addressed. A snapshot file is
  never modified; a source that changes produces a new snapshot beside the
  old one.

## What may change in a 1.x minor release

- New knowledge records, advisories, lifecycle entries — and therefore new
  `dataset_id` values and record counts — at any time.
- New routes, response fields, CLI subcommands and flags, error codes and
  analysis domains. Additions, not redefinitions.
- New contract versions for the `0.x` families, announced in the changelog,
  with records always carrying the version they were written under.
- Human-readable text anywhere: statements, explanations, log lines, CLI
  layout. This is explicitly not contract surface.
- Analysis conclusions themselves, because knowledge changed. A rule that
  concluded `unknown` at `1.0.0` may conclude `violated` at `1.1.0` with
  better evidence. Contract stability never pins truth.

## Deprecation discipline

- **Announce in the changelog** before or with the release that deprecates,
  naming the field, flag or route and its replacement.
- **Keep one minor release of overlap where feasible**: the deprecated form
  keeps working, with its meaning unchanged, alongside its replacement.
  Where overlap is not feasible — a field whose continued presence would be
  a lie — the removal is a major-version event, not a quiet minor one.
- **Never silently change meaning.** A field is added, deprecated or
  removed; it is never repurposed. This is the one rule with no "where
  feasible" attached.
- **Explicitly: no promise of eternal immutability.** A `2.0` of any
  contract may remove and reshape. The promise of 1.x is that change is
  announced, versioned and never retroactive — stored records keep the
  version they were written under and remain readable — not that the shapes
  are frozen forever.

## How a consumer should pin

- **Pin contract versions, not the release.** Check
  `api_contract_version` on the API, or the contract version embedded in
  each record, and fail loudly on a major version you do not know. The DK
  release version in a response is provenance, not a compatibility gate.
- **Pin the release tag for reproducibility.** A downstream product that
  vendors or depends on this repository should pin a release tag and move
  deliberately. That is how a separately governed product built on this
  Core is expected to consume it: as a tagged dependency, never as a fork.
- **Record `dataset_id` for reproducibility, never for compatibility.**
  It tells you exactly which content answered you; it changes whenever
  content or release changes, and that is its job.
- **Never parse human statements.** `statement`, explanation prose, log
  lines and CLI human output may be reworded in any release without notice.
  If a value matters to a machine, it exists as a typed field; if it only
  exists as prose, it is not contract surface — ask for the field instead.
- **Tolerate additions.** Unknown fields in a response you read are future
  additions, not errors.
